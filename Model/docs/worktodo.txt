Method

Standard force balance per Plan v3 physics:

Rolling resistance: F_roll = Crr × m × g = 0.007 × 310 × 9.81 ≈ 21.3 N (speed-independent)

Electrical draw: P_elec = P_mech / motor_eff (0.95)

I'm deliberately ignoring net elevation and wind here — this gives a flat-road, no-wind lower bound, not an exact match. Good question, and tracing through _get_trailered_mask() in tier1.py turns up something concrete — not a vague "it's probably wrong," an actual bug I can point to.

Where it comes from — not the route's physics, a separate KML file

First, to answer "is it directly from the route": no. The route schema (route.py's docstring) defines red_flag_trailer as something that should be computed from physics — P_req(60km/h) > derated P_max. But that's not what's actually running. _get_trailered_mask() instead reads a completely separate file — a "routeshader" KML — passed in via kml_paths[day_index]. It looks for Placemark elements whose name contains the literal string "(False)", pulls their line coordinates, and does a nearest-neighbor match against your route's lat/lon points. So trailering is currently based on manually-drawn zones in a KML someone made, not on the car's actual power/speed capability. That's a real gap from what the schema promises, but not the bug causing your specific symptom.

The actual bug — why one flagged point turns into the entire day

Here's the part that explains Day 8 specifically. After the nearest-neighbor match, there's this:

python

# Enforce the whole stage rule: if any segment in stage is trailered, entire stage is trailered

for seg in route_df["seg_type"].unique():

    mask = route_df["seg_type"] == seg

    if is_trailered[mask].any():

        is_trailered[mask] = True

The intent is clearly "if any point within Stage 1 is flagged, treat all of Stage 1 as trailered — same for Stage 2 independently." That's a reasonable rule on its own.

But go check how seg_type actually gets set when the route is loaded. In _load_route() (both in diagnose_tier2.py and trust_region.py's __main__):

python

part_df = pd.DataFrame({

    ...

    "seg_type":        "stage",

    ...

})

Every single row — Stage 1 and Stage 2 — gets the identical hardcoded string "stage". Not "stage1" / "stage2" as the schema in route.py actually specifies ('stage1' | 'loop_<name>' | 'stage2'). So route_df["seg_type"].unique() returns exactly one value: ["stage"], covering the whole day as a single undifferentiated block.

That means the "whole stage" rule silently becomes a "whole day" rule. If even one point anywhere in Day 8 — Stage 1 or Stage 2 — gets matched to a (False) zone in the KML, this loop marks every point in the entire day as trailered, because as far as this code can tell, Stage 1 and Stage 2 are the same segment. That's exactly your symptom: you said only Stage 1 should be trailered, and the diagnostic shows 557/557 — literally the whole day.

What needs to change

_load_route() needs to actually tag rows with "stage1" vs "stage2" (and presumably "loop_<name>" for loop files) based on which file/portion they came from, instead of the flat "stage" placeholder. Once that's fixed, the whole-stage rounding rule in _get_trailered_mask() will correctly scope itself to just Stage 1 or just Stage 2 independently, rather than blanket-covering the day.

Two more things worth checking once that's fixed, not blocking:

The match threshold — distance_upper_bound=0.001 (in degrees, ≈111m at the equator) for the KDTree query. If the KML's drawn zone boundary is imprecise, points just outside the intended trailered stretch could still match. Worth a sanity check once the seg_type fix lands, since right now it's impossible to tell whether the threshold is also contributing or whether seg_type alone explains everything.

Day 7's opposite problem — you told me Day 7 Stage 2 also needs trailering, but Tier 1 shows trailered=0. With the seg_type bug fixed, it's worth explicitly checking whether Day 7's KML actually has a (False)-named placemark at all, or whether the KML source data itself is missing that zone — two different problems (code bug vs. missing input data) that would need different fixes.

And this is still on top of the earlier finding — even once _get_trailered_mask() is fixed, that mask only feeds Tier 1's coarse diagnostic. forward_sim.py/singleday.solve() still need to actually consume and enforce it for the final optimized output to respect trailering at all.

THE UGLY — newly discovered, deeper than initially thought

"Motor energy" in the report is circular algebra, not real simulator output. The print script computes motor_wh = drain_wh + solar_wh. Whenever drain_wh is 0 (which is most days), motor_wh is mathematically forced to equal solar_wh — this isn't the physics engine confirming itself, it never touches forward_sim's real per-segment energy output at all. We currently cannot verify the energy balance is correct on any "0 Wh drain" day from this report. Needs a real field sourced from forward_sim's actual simulated energy array.

The solar-input calculation reads car attributes that don't exist on CarState, silently falls back to wrong hardcoded defaults, and underestimates solar by ~18%. trust_region.py:

_SOLAR_AREA  = getattr(car, 'solar_area',  5.95)      # real attr: array_area_m2 _SOLAR_EFF   = getattr(car, 'solar_eff',   0.18)      # real attr: array_efficiency = 0.22 _BATT_CAP_WH = getattr(car, 'battery_capacity_wh', 3528.0)  # real: battery_nominal_wh property 

array_area_m2 and the battery figure coincidentally match their fallback defaults, masking the bug — but array_efficiency is really 0.22, not 0.18. Proof: Day 3's reported solar (5921 Wh) × (0.22/0.18) = 7236 Wh, which lands almost exactly on Tier 1's independently-computed Day 3 figure (7175 Wh) from the same run. Every "Solar input"/"Motor energy" figure printed so far has been ~18% low.

Trailering is fundamentally not enforced in the real optimizer, and the Tier 1 diagnostic that IS correct is being corrupted by a segment-tagging bug before it even reaches the final report.

Trailering doesn't come from route physics at all (despite route.py's schema saying it should be P_req(60km/h) > derated P_max) — it's currently sourced from manually-drawn (False)-named zones in a separate "routeshader" KML file, matched to route points via KDTree.

_load_route() hardcodes "seg_type": "stage" for every row, in both Stage 1 and Stage 2, instead of tagging them "stage1"/"stage2" per the schema. This collapses _get_trailered_mask()'s intended "whole STAGE if any point in it is flagged" rule into an unintended "whole DAY" rule. Result: Day 8 (only Stage 1 should be trailered) comes back 100% trailered (557/557 segments) — the bug rounds up in the wrong direction. Day 7 (Stage 2 should be trailered) comes back 0% trailered — needs checking separately whether that's the same bug or missing KML source data.
